# Initial checklist

Build calendar feeds from GTFS data with a Python package, and publish them via a static website.

## Phase 0: Python package

- [x] Add the Python package: `pyproject.toml`, `uv.lock`, `src/` and `tests/`.
- [x] Ignore the build output, `out/`.

## Phase 1: Tooling and test fixtures

- [x] Pin Python, uv and ruff in `mise.toml`, and keep `uv_build` in step with the pinned uv.
- [x] Add `uv sync` to `bin/setup`.
- [x] Add `ruff`, `ruff format` and `ty` to `bin/lint`.
- [x] Add `pytest` to `bin/test`.
- [x] Add a committed synthetic GTFS fixture and test catalog, covering blocks, hub gates, long dwells and after-midnight trips. No 511 data goes in the repo.
- [x] Add a fixture builder, so negative tests can derive broken variants from the synthetic fixture. Loader edge cases keep their in-code GTFS.
- [x] Add a `--operators DIR` option for tests and development, and an end-to-end CLI test on the fixture.
- [x] Test that two builds of the fixture produce identical bytes.
- [x] Add `bin/test-feeds`, called from `bin/ci`: validate the fixture's feeds with ical4j in a pinned container, and check that a known-bad feed fails.
- [x] Add `readme = "README.md"` to `pyproject.toml`.

## Phase 2: Production pipeline

- [x] Decide how a daily rebuild reaches production. GitHub holds the code and runs tests; Railway fetches GTFS and builds feeds nightly. Feeds are build output, not kept in git.
- [x] Decide where the nightly job runs on Railway and where feeds are stored. One service: the container runs the nightly build and serves feeds from a Railway volume. Object storage and a CDN can come later.
- [ ] Configure the Railway service: the volume at `/feeds`, the Transitland API key variable, watch patterns for the Python build inputs, and a draining time of at least 15 s so a redeploy can stop a running build cleanly (Railway's default is 0).
- [x] Fetch the latest GTFS feed version from Transitland: `transit-cal fetch`.
- [x] Publish a validated feed tree atomically and prune old releases: `transit-cal publish`.
- [ ] Store the Transitland API key as a secret where the build runs, never in the repo.
- [x] Add `bin/build-feeds`, following the deploy decision: it runs the image's `build-feeds` (fetch, build, validate, publish under one lock) against `out/feeds`; `bin/run-image` serves them.
- [ ] Pin each build's inputs: the GTFS version and the first service day.
- [ ] Check each new GTFS version against the operators' published timetables before publishing.
- [x] Validate the real feeds against RFC 5545 before publishing: ical4j in the image, before `transit-cal publish`.
- [x] Rebuild the feeds daily. Each feed's window moves forward a day, so rebuild even when the GTFS is unchanged.
- [x] Serve `.ics` files as `text/calendar`, locally and in production.
- [x] Check the `.ics` content type in `bin/test-image`, once feeds are in the image.
- [x] Keep serving the last good feeds when a fetch or build fails.
- [ ] Alert on a failed fetch, build or deploy.
- [ ] External monitoring, likely Checkly: check the site, a feed, and that `/feeds/current` is under 12 hours old. Railway's healthcheck runs only at deploy time.
- [x] Run the build in the container on fixed UTC slots, plus a catch-up build at startup when `current` is missing or stale, under s6 supervision.
- [ ] Keep pinned versions current: Renovate PRs for image digests, the jar lock, uv, Node and GitHub Actions; an SBOM and vulnerability scan in CI.
- [ ] Check whether Railway offers a read-only root filesystem, dropped Linux capabilities or egress limits; those, not removing tools, would limit a compromised process.
- [ ] Warn before an operator's published data runs out, so subscribers never see an unexplained empty calendar.
- [ ] Decide whether the CLI's summary output should be structured log lines.

## Phase 3: Website

- [ ] Add a page per route in the 11ty site. Decide how feed data reaches 11ty, the page layout and the page URLs.
- [ ] Link each feed to its route page (`page_url` in `ics.py`).

## Phase 4: Docs

- [ ] Record the feed URL and event UID decisions in `docs/memory/architecture.md`.
- [ ] Record the Python stack in `architecture.md`, and update its repo layout.

## Phase 5: Later work

- [ ] Generalize the route model beyond hub-and-spoke, before adding rail or bus operators.
- [ ] Limit each route's feed to its own route's trips.
- [ ] Accept blank stop times at non-timepoint stops.
- [ ] Honour GTFS `pickup_type` and `drop_off_type`.
- [ ] More tests: UID stability and more `legs.py` edge cases.
- [ ] Generate operator catalog files from Transitland data with a CLI command.
- [ ] Run MobilityData's gtfs-validator on each new GTFS version.
- [ ] Document data sources: attribution, licence terms and Transitland's role.
- [ ] Ask MTC whether a small GTFS extract may be committed for offline tests. 511's data agreement requires sublicensees to accept its terms.
- [ ] List each data source in the README, and whether it is upstream or curated by hand.
